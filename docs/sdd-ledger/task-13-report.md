## Integration bugs found and fixed
1. **proot could not load on Android: `libandroid-shmem.so` missing** (`fix: bundle libandroid-shmem ...`, 9ccac11). Every dsh start ended at once with `CANNOT LINK EXECUTABLE ".../lib/x86_64/libproot.so": library "libandroid-shmem.so" not found: needed by main executable` (CI run 41543808266, error log). Root cause: Termux's proot (both aarch64 and x86_64 builds) has `DT_NEEDED` libtalloc, libandroid-shmem and libc; Task 3 shipped only libtalloc (its report said shmem was not an ELF NEEDED, which `readelf -d` disproves for both arches). Fix: `proot.gradle.kts` fetches the pinned `libandroid-shmem_0.7` debs (sha256 from Termux's `Packages` index: aarch64 `0da3a24d...7ff6`, x86_64 `ffa9e4c8...5797`) and installs `lib/libandroid-shmem.so` next to proot (its own NEEDED are only Android's `liblog.so` and `libc.so`). Test: `BundledNativeLibsTest` parses the ELF dynamic section of every bundled `.so` for both ABIs and requires each `DT_NEEDED` to be bundled or an NDK system library (RED before the fix: "arm64-v8a/libproot.so needs libandroid-shmem.so ..."; GREEN after). The E2E suite is the runtime proof. This affects the real phone exactly the same way (arm64 build has the same NEEDED).
2. **Main screen claimed Ready before dsh's page had loaded** (`fix: the main screen says Ready only after ...`, 9347e54). A second `startDsh()` for the same dsh (the give-up collector racing the explicit restart, or a stop/start of the screen) found the launch URL already loaded and switched to Ready without `onPageFinished`. It surfaced as the flaky unit test `MainActivityTest.rollbackAfterAGiveUpWithNothingToGoBackToWhileDshRunsShowsDsh` (failed locally once and on CI run 41547715244's android job: expected Loading, was Ready). Fix: `MainActivity` tracks `pageFinished` (set in `onLoaded`, cleared on every `loadUrl`); the "same URL" path goes to Ready only when the page has finished. Test: `MainActivityTest.aSecondStartOfTheSameDshBeforeThePageFinishedStaysLoading` (RED on the old code: "expected Loading but was Ready"; GREEN after; it also checks that returning from the background with a loaded page still goes straight to Ready).
3. **Test-suite starvation by orphaned fake processes** (same commit). `DshControllerTest`, `DshServiceTest` and `HeartbeatWorkerTest` launched fake dsh as `sh -c '...; sleep 30|60'`; killing `sh` left the `sleep` holding the pipes, so the controller's blocking reader coroutines stayed parked on `Dispatchers.IO` (the cause Task 11a found and fixed only in its own test). Fix: `exec sleep` in those scripts (test code only). Two consecutive `--rerun-tasks` full runs: 559 tests, 0 failures. (I first blamed this for the `DshServiceTest` flake too; it was not the cause. See bug 4.)
4. **A dsh that died while its start was being checked was published as running** (`fix: a dsh that dies while its start is being checked ...`, fb45859). `DshController`'s exit watcher decided "unexpected exit" by `run.info != null` without the state lock. When dsh exited after printing its launch line but before `start()` published the run, the watcher took the exit as expected and tore down. `start()` then published the dead run: `isRunning` stayed true, `ensureRunning()` returned a dead dsh, and no exit listener ran, so `DshService`'s CrashPolicy never heard of it. It showed up on CI run 41552514871 (and once locally) as `DshServiceTest.afterAGiveUpARetryRunsUnderTheServiceAgainAndALaterCrashIsHandled` never reaching the give-up: its fake dsh exits right after the launch line and the health check is instant. On a phone the window is the time between a passing health check and the publish. Fix: the watcher records `exitCode` and decides under `stateLock`; the publish block (same lock) throws `IllegalStateException("dsh exited with code N before it was ready")` when `exitCode` is set. So exactly one side reports the death: the start, or the exit listeners. Test: `DshControllerTest.aDshThatDiesBeforeItIsPublishedIsAFailedStartNotARunningOne` (a fake dsh that dies 1 s after its launch line; the health check waits until the process is dead and the watcher has torn down). RED on the old code: "a dead dsh was published as running (got null)". GREEN after: the start fails, `isRunning` is false, no exit listener call, and the next start is normal. Full suite twice with `--rerun-tasks`: 560 tests, 0 failures.
5. **Task 11a's instrumentation test read the URL too early and printed the login token** (`test: WebView instrumentation tests ...`, 824c652). `anExternalLinkDoesNotNavigateTheWebView` took the "before" URL while the WebView was still on the launch URL (dsh answers it with a 303 to `/`), so the comparison failed, and its `assertEquals`/message put both URLs, token included, into the test report (CI run 41547715244, artifact `e2e-reports`; that token belonged to a throwaway emulator dsh that no longer exists). Fix: both tests wait until the URL is on dsh without `token=` and `document.readyState == "complete"`; assertions carry no URL.

Not bugs, observed on the emulator and left as they are: SELinux denies hard links in the app's data dir (`avc: denied { link }` for git/perl hard links); `RootfsInstaller` falls back to copying as designed. The linker's probe of `/data/local/tests` is denied (harmless). CI infrastructure (not app bugs): the stock runner has ~5 GB free and the emulator needs 1.2 x disk-size for userdata (run 41538478337 never booted: "Not enough space to create userdata partition"), so the job deletes unused toolchains first (~39 GB free); the runner has 2 cores, not 4.

## Not verified on a real S25 Ultra (arm64, Android 17)
- Anything arm64: the arm64 proot/libtalloc/libandroid-shmem set and the arm64 rootfs only ran under qemu in the rootfs smoke test (chroot, not proot), never on an arm64 kernel with Android's SELinux/seccomp.
- Android 17 policy differences from API 34: W^X/exec rules for app data (proot's loader mmaps the guest binaries; works on 34), seccomp filter changes, ptrace restrictions, and a possible 16 KB page size (Termux binaries and the Debian/Node userland were not checked for 16 KB alignment). Samsung's own restrictions (phantom process killer behaviour with the user's setting, battery optimisation, background starts) are untested.
- Real model traffic: DeepSeek's actual SSE (thinking blocks, cache usage fields), real keys, real costs, rate guard and daily cap under load; web search; Anthropic route.
- Real `npm view`/`npm install` inside proot for an update (test 5 fakes the GuestCommand by design), network/DNS from the guest (`GuestNetworkFiles`), and the heartbeat under real WorkManager scheduling/Doze (test 4 runs the worker directly).
- UI on a real GPU/WebView version, notification taps (deep link, rollback action), the share sheet, downloads, the APK self-update hand-off, Settings actions (Apply/restart/update/rollback) through the screen.
- Rootfs install time on the phone (179-218 s on the emulator with pure-Java xz; hard links become copies there too).

## Concerns
1. The token printed by the old 11a test is in the `e2e-reports` artifact of run 41547715244 (retention 7 days). It was the login token of an emulator-only dsh that was killed with the emulator, so it opens nothing; deleting that artifact by hand would remove it entirely.
2. The rootfs CI cache key covers `rootfs/**` and `plugins/**` only: an unchanged pair reuses a rootfs whose Debian packages were fetched when it was built. The release workflow still builds fresh. Changing `rootfs/versions.env` (or any rootfs script) invalidates it.
3. Task 3's report statement that libandroid-shmem is "not an ELF NEEDED" was wrong; anything else derived from it (e.g. licence notices for bundled Termux libraries) should now include libandroid-shmem.
4. The Robolectric suite still runs real `sh` processes with timing waits. Both CI flakes found here came from real production races (bugs 2 and 4) and are fixed, but the pattern stays timing-sensitive on slow runners.
5. `E2eRunner` replaces the default runner for all instrumentation tests in this APK (both classes need it: they share the process and the controller).
